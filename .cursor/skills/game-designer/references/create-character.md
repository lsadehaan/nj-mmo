# Recipe: Create a Character (player or NPC)

This is the exact, repeatable procedure for adding or skinning a humanoid the player controls or interacts with. Read `../SKILL.md` first (the three-layer model + golden rules). Do the steps in order. Each step has a **Done when** you must satisfy before moving on.

For a quick swap among assets that already share the rig (KayKit Knight/Mage/Rogue/Hooded/Barbarian), skip to step 3 — it is a one-line `DEFAULT_CHARACTER` change in `client/src/scene/player-avatar.ts`.

---

## Step 1 — Source the best-matching rigged GLB (fidelity is law; reuse a pack)

Find the **closest available representation of this specific character** with at least idle, walk, an attack, and a death animation (cast optional — fall back to attack). Curated-first: KayKit, Quaternius, Mixamo — vendor the rigged GLB locally, then wire it in. The pack is **not** the spec: a barbarian is not a "Gremlin" and a mage is not a "merchant" just because the file loads. If no good match exists, **search harder, source another pack / AI-generate a rigged mesh, or halt and surface the gap — never copy another entity's GLB or drop in a wrong-category default** (golden rule 2). License may be relaxed pre-live (unlicensed/unknown/proprietary placeholders OK *if* they actually look right and are tracked for pre-launch replacement); **fidelity may not.**

> **Rigged ≠ static — do NOT hand-author this in code.** Static props (buildings, rocks) may be hand-built from Three.js geometry and exported to GLB (see `create-prop.md`). **Characters, NPCs, and monsters may not** — they need a skinned skeleton plus named animation clips (`idle/move/attack/cast/die`) that the `AnimationMixer` drives, and hand-coding a rig + skin weights + baked clips by hand is not viable. For rigged entities, **reuse a pack** (step 1) is mandatory; the only fallbacks are *another* pack or an **AI-generated rigged** model — never code-authored geometry, and never a static (clip-less) stand-in.

```bash
mkdir -p client/public/models/characters && cd client/public/models/characters
BASE="https://raw.githubusercontent.com/KayKit-Game-Assets/KayKit-Character-Pack-Adventures-1.0/main/addons/kaykit_character_pack_adventures/Characters/gltf"
curl -sSL -o Rogue.glb "$BASE/Rogue.glb"
# Always vendor the license next to the asset:
curl -sSL -o LICENSE.txt "https://raw.githubusercontent.com/KayKit-Game-Assets/KayKit-Character-Pack-Adventures-1.0/main/LICENSE.txt"
```

**Done when:** the `.glb` is under `client/public/models/characters/`; if it ships a license, `LICENSE.txt` sits beside it, otherwise the unlicensed placeholder is noted for pre-launch replacement.

## Step 2 — Inspect the GLB (the model names the tracks, not you)

Read the embedded animation names and bounding box so the clip map and scale are based on reality:

```bash
node -e 'const fs=require("fs");const f=process.argv[1];const b=fs.readFileSync(f);
const j=JSON.parse(b.slice(20,20+b.readUInt32LE(12)).toString("utf8"));
console.log("anims:",(j.animations||[]).map(a=>a.name).join(" | "));
console.log("meshes:",(j.meshes||[]).length,"nodes:",(j.nodes||[]).length);' client/public/models/characters/Rogue.glb
```

For size/feet, render once in the lab (step 7) which logs `MODEL <name> size=… minY=…`. `minY≈0` means the origin is at the feet (most KayKit/Quaternius rigs).

**Done when:** you have the literal list of track names and know the model's height and whether its origin is at the feet.

## Step 3 — Map the asset tracks to our vocabulary

The only translation layer between an asset and the engine. If the new asset shares the KayKit universal rig, reuse `KAYKIT_CLIP_MAP` in `client/src/scene/creature/mesh-character.ts`:

```ts
export const KAYKIT_CLIP_MAP: Record<ClipName, string> = {
  idle: 'Idle',
  move: 'Walking_A',
  attack: '1H_Melee_Attack_Chop',
  cast: 'Spellcast_Shoot',
  die: 'Death_A',
};
```

If the asset uses different names, pass a custom `clipMap` to `createMeshCharacter`. To select a character that shares the rig, set `DEFAULT_CHARACTER` in `player-avatar.ts` (e.g. `'Rogue'`). For a per-player choice later, thread a `character` option through `createPlayerAvatar`.

**Done when:** every one of `idle/move/attack/cast/die` maps to a real track name in this GLB. No invented names.

## Step 4 — Body backend (already built; reuse it)

`createMeshCharacter(url, { clipMap, scale })` in `client/src/scene/creature/mesh-character.ts` loads the GLB, builds an `AnimationMixer`, and exposes `play(clip)` (crossfade; one-shot for attack/cast/die, loop for idle/move), `update(dt)`, and `setTime(s)` (deterministic posing for screenshots). You normally do not edit this file — only its clip map. Touch it only to add a capability (e.g. a clone-per-instance path for monsters — see the monster recipe).

**Done when:** the character renders via the existing backend with no backend edits, OR your backend change is covered by the monster recipe's clone requirement.

## Step 5 — Wire the body to the brain + signal

For the player this is `client/src/scene/player-avatar.ts`. It must, each frame:

1. Read the server signal (`action`, `actionSeq`) from `sync()` (fed by `client/src/net/room.ts` → `renderer.syncLocalPlayer`).
2. Derive `locomotion` from server position deltas with a **coast timer** (`MOVE_COAST_MS`) — stay `move` across the gaps between server syncs, decay to `idle` after movement stops. (The server stops broadcasting position when idle, so a timeout — not a zero-delta sync — returns you to idle. Do not recompute locomotion per render frame from the mesh position; that flickers.)
3. Run the brain: `stepAnimation(state, { action, actionSeq, locomotion, nowMs })`.
4. `character.play(clip)` then `character.update(dt)`.
5. Face movement direction; during `attack`/`cast`, face the current target mob.

Also surface the clip for tests: `__GAME_STATE__.player.action` (see `client/src/test-hook.ts` `GameStatePlayer.action`).

**Done when:** moving the player plays `move`, stopping returns to `idle`, and a server attack/cast/death plays the one-shot.

## Step 6 — Tune scale, feet, facing (by rendering, not guessing)

Three knobs in `player-avatar.ts`: `MODEL_SCALE` (world size — KayKit ≈ 2.69u at scale 1; keep the hero readable in the follow cam), `FEET_OFFSET_Y` (server y is body-center; drop the mesh so feet touch ground), and facing (`group.rotation.y` from the movement/target direction; apply any model-forward correction to the model inside the group, not to the logical yaw).

**Done when:** in a rendered frame the character stands on the ground (not floating/sunk), is a sensible size next to buildings/NPCs, and faces where it walks.

## Step 7 — Visual gate (BLOCKING: structural + fidelity)

Two layers, both must pass (golden rule 4). A human is not required; **real perception is.**

```bash
# Layer 1 — structural (deterministic, catches copies/empties/mis-rigged props)
node scripts/visual-gate.mjs

# Layer 2 — render for fidelity. Start the client dev server if not running:
npx vite --port 4200 --strictPort     # from client/, background it
# render idle/move/attack/cast/die to /tmp/char-shots/<Char>-<clip>.png
LAB_BASE=http://localhost:4200 LAB_CHAR=Rogue node scripts/shoot-character.mjs
```

Then **actually read each PNG** (idle, move, attack, cast, die) and judge it against the real description of this character — *"is this a good-faith best match for `<entity>`, or a generic stand-in?"* A captured screenshot you never look at is not evidence. The lab page is `client/character-lab.html` + `client/src/character-lab.ts`; it accepts `?char=&clip=&t=&angle=&auto=`. Human approval is welcome but optional.

**Done when:** `visual-gate.mjs` is green AND every clip has been rendered and *perceived* as a faithful match for the entity (mismatch = FAIL, fix the asset).

## Step 8 — Prove in-game + run the gate

```bash
npx nx run-many -t test lint build --projects=client,game-core
```

Client unit tests cover `__GAME_STATE__` hook wiring (`test-hook.spec.ts`, `wire-room.spec.ts`).

**Done when:** `test lint build` are green.

## Step 9 — Record decisions

If you changed anything architectural (a new asset family, a new clip map convention, a backend capability), add/append an `AD-***` in `.specs/STATE.md` and tick the relevant `.specs/ROADMAP.md` item. A pure asset swap that fits existing decisions needs no new AD.

**Done when:** STATE/ROADMAP reflect reality.

## NPC note

NPCs follow the same recipe but are simpler: no player input and usually no combat signal. They typically only need `idle` (and `move` if they wander). Render them through `createMeshCharacter` from the NPC renderer (`client/src/scene/npc-renderer.ts`), keep them server-positioned, and you can omit attack/cast/die from the clip map (fall back to `idle`). Still run the visual gate.

**NPCs are rigged characters, so the same "reuse a pack, do not hand-author" rule applies** (see Step 1's callout). Even an idle-only NPC needs a real skinned rig with an `idle` clip — a hand-built, clip-less mesh would stand frozen and is not acceptable. Source the closest-matching rigged GLB from the packs (KayKit character packs are the current NPC source, e.g. Roxxy); if none fits, use another pack or an AI-generated rigged model. The code-authoring fallback is for **static props only**.

## Remote-player note

Other players are the **same human avatar** as the hero, just wired differently. Reuse `createMeshCharacter` (one instance per remote session — this is the *single-load* path, not the monster clone path; each remote player is unique). Wire it in `client/src/scene/remote-players.ts` (replacing the capsule), and differ from the local player in three ways:

1. **No local input.** Locomotion is derived from the *replicated* server position deltas (same `MOVE_COAST_MS` coast timer as the hero), not from clicks.
2. **Action from replicated state.** Read each remote player's `action`/`actionSeq` from room state (the same fields `PlayerState` already carries), run `stepAnimation`, `play`/`update`.
3. **No follow camera.** You only place + animate the mesh.

Equipped-weapon meshes (e.g. Squire's Sword) attach to the avatar's hand — see `create-attachment.md`. **Done when:** a second session renders a non-capsule avatar that walks, stops, and plays attack/cast/die from replicated state.
